# Benchmark archive: the LLVM switch (B7 and B8, 2026-11-09)

`benchmarks/report.md` is generated by `benchmarks/run.sh`, which measures the
current compiler and nothing else. These two sections were produced by
`python3 benchmarks/llvm_readiness/run.py --runs 30 --c` and `--runs 25 --c`
while LLVM was replacing Cranelift, and they are kept here because
`crates/kode-llvm/B7.md` and `B8.md` cite them. The Cranelift column cannot be
re-measured: `refactor: remove cranelift backend` deleted the backend in B8.

## LLVM versus Cranelift (B7, 2026-11-09)

Produced by `python3 benchmarks/llvm_readiness/run.py --runs 30 --c` on the
machine above. Both backends are built with `kode build --release --backend=...`;
each case is checked for identical output before timing. Wall clock is the
hyperfine median of 30 runs after 2 warmups; C is `cc -O2` where a `main.c`
exists.

| case | Cranelift ms | LLVM ms | LLVM/Cranelift | C ms | LLVM/C |
| --- | ---: | ---: | ---: | ---: | ---: |
| fib (38) | 130.4 | 3.9 | 0.03 | 57.9 | 0.07 |
| loop_mod | 31.4 | 14.6 | 0.47 | 11.3 | 1.29 |
| mandel | 16.0 | 13.9 | 0.87 | 11.2 | 1.24 |
| sieve | 35.2 | 38.9 | 1.11 | 14.7 | 2.64 |
| collatz | 276.4 | 209.4 | 0.76 | 152.1 | 1.38 |
| lists (1M ints) | 3.5 | 3.7 | 1.05 | — | — |
| packed bools (1M) | 2.8 | 3.3 | 1.16 | — | — |
| maps (100k writes) | 42.5 | 42.6 | 1.00 | — | — |
| json (20k parses) | 116.8 | 110.6 | 0.95 | — | — |
| strings (200k interpolations) | 128.0 | 115.1 | 0.90 | — | — |
| objects (1M allocations) | 50.3 | 70.0 | 1.39 | — | — |
| tasks and channels | 200.3 | 196.3 | 0.98 | — | — |
| wordcount app (3 MB) | 860.2 | 855.0 | 0.99 | — | — |

Reading these:

- **fib is not a runtime win, it is clang's optimizer.** The LLVM object calls
  `fib(n-2)`, `fib(n-3)` and `fib(n-4)` at each level (verified in the
  disassembly), so the recursion tree is far shallower; Cranelift emits the plain
  double recursion. Repeated runs agree: `fib(45)` takes 4.61 s with Cranelift and
  0.39 s with LLVM, both printing 1134903170. The benchmark therefore no longer
  measures the same call tree on both backends.
- **loop-heavy code** (loop_mod, collatz, mandel) is 13–53% faster with LLVM,
  still 1.24–1.38x behind C.
- **Runtime-bound code** (maps, JSON, strings, tasks/channels, the wordcount
  application) is at parity, within ±16%: those paths call the same runtime
  functions, so the backend matters little.
- **objects** showed 1.39x in the 30-run table but repeated 20-run measurements
  gave 44.5/45.5, 54.5/57.7 and 54.3/51.8 ms, i.e. parity; the machine is a
  laptop and that case is noisy. Allocation alone measured 44.5 vs 49.8 ms
  (1.12x); the method-call-only loop was faster with LLVM (3.1 vs 1.3 ms).
- **No case is more than ~1.4x slower**, and no universal "LLVM is faster" claim
  is supported: sieve is 11% slower than Cranelift and 2.64x behind C.

## LLVM alone (B8, 2026-11-09)

Cranelift was removed in B8, so this table has no Cranelift column. Produced by
`python3 benchmarks/llvm_readiness/run.py --runs 25 --c` on the same machine;
hyperfine median of 25 runs after 2 warmups, `kode build --release`, C `-O2`.

| case | LLVM ms | C ms | LLVM/C |
| --- | ---: | ---: | ---: |
| fib (38) | 3.5 | 57.5 | 0.06 |
| loop_mod | 11.5 | 11.1 | 1.03 |
| mandel | 12.6 | 10.9 | 1.15 |
| sieve | 29.6 | 11.7 | 2.52 |
| collatz | 196.8 | 147.2 | 1.34 |
| lists (1M ints) | 3.9 | — | — |
| packed bools (1M) | 3.3 | — | — |
| maps (100k writes) | 42.2 | — | — |
| json (20k parses) | 89.7 | — | — |
| strings (200k interpolations) | 87.9 | — | — |
| objects (1M allocations) | 44.5 | — | — |
| tasks and channels | 126.6 | — | — |
| wordcount app (3 MB) | 648.3 | — | — |

Compared with the B7 LLVM column, every case is the same or faster (fib 3.9→3.5,
collatz 209→197, sieve 38.9→29.6, objects 70.0→44.5, tasks 196→127, wordcount
855→648 ms). The objects case confirms that B7's 1.39x was measurement noise, not
a regression: this run measures 44.5 ms, the same as the repeated B7 re-runs.

fib is still dominated by clang's recursion rewriting (B7 disassembly): the
benchmark does not measure the naive call tree, so its LLVM/C ratio is not a
general speed claim.
