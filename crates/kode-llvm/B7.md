# B7: production readiness and the default switch

Stage B7 of ADR 0035. B1–B6 built the backend and proved it against Cranelift on
this machine; B7 checks the things a default backend must survive, then makes
LLVM the default and keeps Cranelift selectable.

## Platform and toolchain matrix

| Target | Compiler | Backend suite | Notes |
|---|---|---|---|
| macOS 27.2 arm64 (Apple silicon) | Apple clang 21.0.0, rustc 1.97.1 | 7/7 conformance tests, 186 workspace tests | the primary machine |
| Linux arm64 (Docker, native) | Debian clang 19.1.7, rustc 1.97.1 | 7/7 conformance tests, 197 workspace tests | full gate re-run after the switch |
| Linux x86-64 (Docker under Rosetta) | Debian clang 19.1.7 | 45/45 backend parity, 0 mismatches | the repo's own `run_pass` fails here for both backends, see below |
| Windows | not tested | — | no toolchain on this machine |

That is three target/compiler combinations and two clang versions. Windows and
native x86-64 hardware are **not** validated; do not read this as cross-platform
support for them.

**Pre-existing platform bug found on Linux x86-64.** `tests/run-pass/process.kode`
expects `exec("kode-no-such-program-9f3a")` to raise. Under Docker's Rosetta
emulation it does not: both backends print `false`, and the repository's own
`cargo test -p kode-cli --test conformance run_pass` fails with Cranelift too.
This is runtime/platform behaviour, outside B7's boundary (no runtime changes),
and it is not an LLVM divergence: all 45 run-pass programs agree between backends.
It needs a runtime fix and a decision (skip-os marker or exec error handling) as a
separate change.

## Conformance

`cargo test -p kode-cli --test llvm_conformance` — 7 tests: 45 run-pass programs
in three batches, 8 examples, 98 compile-fail programs, unknown-backend handling,
and the default-is-LLVM test. Every program runs with `KODE_LEAK_CHECK=1` under a
30 s timeout; exit status, stdout and stderr must match across backends and the
run-pass output must match the checked-in `.out`.

A bug in the B6 version of that harness was found and fixed here: it wrote the
compile-fail object to `/dev/null`, which fails on macOS for the wrong reason and
hid `w0001_unused.kode` (a warning-only fixture that legitimately builds). The
test now mirrors the repository runner: `check --strict --format=json`, expecting
the code from the `.err` file, compared between backends.

## Benchmarks

Full table and commentary: `benchmarks/report.md` ("LLVM versus Cranelift") and
`benchmarks/llvm_readiness/run.py`, which rebuilds and re-measures everything.
Summary: loop-heavy code is 13–53% faster with LLVM and 1.24–1.38x behind C;
runtime-bound code (maps, JSON, strings, tasks/channels, the wordcount
application) is at parity; sieve is 11% slower than Cranelift; the fib numbers are
explained by clang unrolling and reassociating the recursion, not by a faster call
path.

## The switch

| File | Change |
|---|---|
| `crates/kode-cli/src/args.rs` | `Backend::default()` is `Llvm`; help text says so |
| `crates/kode-cli/tests/llvm_conformance.rs` | new test proves the default by behaviour: with `KODE_CLANG` pointing nowhere, a default build exits 1 with the LLVM message and produces no output, while `--backend=cranelift` still builds |
| `README.md`, `CHANGELOG.md`, `docs/PLAN-v1.md`, `docs/adr/0035-llvm-backend.md` | document LLVM as default and Cranelift as the transitional option |
| `benchmarks/llvm_readiness/` | the benchmark set and its runner |

No silent fallback exists in either direction: LLVM without clang is an error,
and `--backend=cranelift` never invokes clang.

## Cranelift removal (not done here)

Removing Cranelift is B8 and needs its own approval. It would touch:

- `crates/kode-codegen/` (whole crate, plus `crates/kode-cli/Cargo.toml`)
- `Cargo.toml` workspace members and `Cargo.lock`
- `crates/kode-cli/src/{args.rs,main.rs}` (drop the enum, the flag and the
  dispatch)
- `crates/kode-llvm/tests/{ir_runtime,runtime_semantics,ir_collections,collections,ir_objects,objects,ir_errors_concurrency,errors_concurrency}.rs`
  and `benches`-style comparisons that use Cranelift as the oracle, plus the
  B3–B5 stage documents that report its numbers
- `benchmarks/llvm_readiness/run.py` (Cranelift column), `benchmarks/report.md`
- `README.md`, `CHANGELOG.md`, `docs/PLAN-v1.md`, `docs/adr/0035-llvm-backend.md`
  and any doc that says "Cranelift is the backend"

Rollback concerns while it remains: the flag is the only behaviour difference, so
a regression in LLVM codegen can be worked around per build with
`--backend=cranelift`. Binary consumers see one extra clang dependency
(build-time) and the same runtime archive.
