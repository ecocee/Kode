# B9: platform CI and runtime hardening

Follows B8 (`feat/llvm-only`, `ead0818`). Commits: the `kode-link` rename, the
CI workflows, and the hardening/diagnostics/build-discovery/docs work.

## 1. CI

`.github/workflows/ci.yml` (rewritten) has one matrix, four native runners, no
skip list and no `continue-on-error`:

| Job | Runner | Architecture asserted |
|---|---|---|
| `test (linux-x86_64)` | `ubuntu-latest` | `x86_64` |
| `test (linux-aarch64)` | `ubuntu-24.04-arm` | `aarch64` |
| `test (macos-aarch64)` | `macos-14` | `arm64` |
| `test (windows-x86_64)` | `windows-latest` | `x86_64` |

Every job installs or verifies its tools explicitly, prints `uname -m`,
`rustc`, `cargo`, `clang` and `cc` versions, and then runs in order:

1. `cargo build --workspace`
2. `cargo clippy --workspace --all-targets -- -D warnings`
3. `cargo test --workspace` with `KODE_LEAK_CHECK=1`
4. `cargo test -p kode-cli --test llvm_conformance` (run-pass `.out`, compile-fail `.err`)
5. `kode fmt tests/run-pass examples --check`
6. `cargo build --release -p kode-cli`
7. build and run `examples/hello.kode` with `target/release/kode`, then `kode doctor`

Tool installation per OS: `clang gcc libc6-dev` from apt on Linux; Chocolatey
`llvm` plus MSYS2 UCRT64 gcc on Windows (with the GNU Rust toolchain, because the
runtime archive must be linkable by MinGW); on macOS the system Command Line
Tools are verified (`xcode-select -p`, `clang --version`, `cc --version`) rather
than installed, because they cannot be installed non-interactively.

`release.yml` gained an explicit clang install for its Linux job: its smoke test
runs the built compiler, which now always needs clang.

The arm64 Linux runner is a Microsoft-hosted runner available to public
repositories. In a private fork that job cannot start; the alternative is a
self-hosted `aarch64` runner. This is recorded in `docs/platforms.md`.

## 2. Runtime and spawn audit

Crates that start processes: `kode-rt` (`exec`), `kode-llvm` (clang),
`kode-link` (linker), `kode-cli` (`doctor`, and the program `kode run` builds).

| Where | Call | Failure path | Reaping |
|---|---|---|---|
| `kode-rt/src/process.rs` | `Command::output()` | `Err` → raises `cannot run \`prog\`: …` | `output()` waits |
| `kode-llvm/src/clang.rs` | `Command::output()` | `ClangError::NotFound` / `Failed` / `Io` | waits |
| `kode-link/src/link.rs` | `Command::status()` | `could not start the linker` / `failed with <status>` | waits |
| `kode-cli/src/doctor.rs` | `Command::output()` | reported as "did not run" | waits |
| `kode-cli/src/main.rs` (`run`) | `Command::status()` | `cannot run the program: …` | waits |

Every child is waited for by `output()`/`status()`, so there are no zombies and
no orphaned grandchildren from Kode's own calls; `exec` also closes stdin and
lets `std` drain stdout and stderr concurrently, so a child cannot deadlock on a
full pipe.

The only `unsafe` block in this area is the `pre_exec` hook, now written once in
`kode_link::force_fork_exec` and once in `kode-rt` (which, as a dependency-free
static library, cannot import it). Both carry a `SAFETY` comment: the closure
runs in the forked child where only async-signal-safe work is allowed, and it
does nothing — no allocation, no locks, no libc calls — then reports success.
The hook exists because `posix_spawn` reported success for a child whose `exec`
failed (B8); it forces the fork path, where the exec errno comes back through a
pipe. Windows has no fork and gets a no-op.

`kode-cli`'s `doctor` now uses the same helper, so a missing `cc` is described as
missing rather than as a program that exited 127.

## 3. Diagnostics

| Case | Expected | Test |
|---|---|---|
| clang missing | exit 1, `the LLVM backend needs …`, no output | `a_missing_clang_is_actionable_and_leaves_no_artifact` |
| clang not executable (`chmod 644`) | exit 1, `could not be run`, no output | `a_clang_that_cannot_be_executed_is_actionable` |
| invalid clang path | same as missing | `a_missing_clang_is_reported_before_any_work` |
| invalid LLVM IR | `ClangError::Failed` with clang's stderr, `.ll` and `.o` removed | `invalid_ir_is_reported_and_cleaned_up` |
| linker missing | exit 1, `could not start the linker …`, install hint, no output | `a_missing_linker_is_actionable` |
| linker fails | exit 1, ``the linker `…` failed with exit status: 7``, no output | `a_failing_linker_is_reported` |
| failed build leaves nothing | `!exe.exists()` in every case above | all of the above |

The linker tests use a stub script that exits 7, not `/bin/false`: macOS has no
`/bin/false`.

## 3b. `cargo build --release` from a clean tree

Reproducing CI by hand turned up a second build bug. `crates/kode-cli/build.rs`
embeds `libkode_rt.a` and used to look for it only in `target/debug` and
`target/release`. `kode-rt` is a `staticlib` **build dependency**, and Cargo does
not uplift a build dependency's archive out of `deps/`, so a tree with no earlier
debug build has only `target/release/deps/libkode_rt-<hash>.a`. `cargo build
--release` alone therefore panicked with "could not find libkode_rt.a under
target", while `cargo build && cargo build --release` worked by accident.

The build script now derives the profile from `PROFILE`, honours
`CARGO_TARGET_DIR` (previously it always looked under `<workspace>/target`), and
falls back to the newest `libkode_rt*.a` in the matching `deps/` folder. Verified
by deleting `target/release` and running `cargo build --release` (1m15s, then 25s
incremental), by building with `CARGO_TARGET_DIR=/tmp/kode-b9-target`, and by
running the resulting binaries.

## 4. Earlier Clippy failure (found by reproducing CI)

The Linux containers ship Rust 1.99, whose Clippy has
`chunks_exact_to_as_chunks`; the repository's `sha256.rs` used `chunks_exact` at
three constant-size call sites, so `-D warnings` failed on CI but not on the
older local toolchain (1.97). The three sites now use `slice::as_chunks`, which
is available since Rust 1.88 and therefore inside the workspace MSRV of 1.91.
The FIPS-180 and RFC 4231/7677 vectors still pass, so the SHA-256, HMAC and
PBKDF2 output is unchanged. This is the reason the B9 commit also touches
`crates/kode-rt/src/sha256.rs`.

## 5. Validation

CI itself has **not run**: the branch is local, nothing was pushed, and `gh` is
not installed. What was run is the exact command sequence above, by hand:

| Target | Toolchain | Result |
|---|---|---|
| macOS 27.2 arm64 (native) | rustc 1.97.1, Apple clang 21.0.0 | 191 tests, 10/10 conformance, fmt clean, release build, hello prints `hello world` |
| Linux arm64 (native Docker) | rustc 1.99.1, Debian clang 19.1.7, gcc 14.2.0 | 202 tests, 10/10 conformance, clippy clean, fmt clean, release build, hello prints `hello world` |
| Linux x86-64 (**emulated**, Rosetta) | rustc 1.99.1, Debian clang 19.1.7, gcc 14.2.0 | 202 tests, 10/10 conformance, clippy clean, fmt clean, release build, hello prints `hello world` |

The test totals differ because some tests are `#[cfg(unix)]` or `cfg(target_os)`.
The Linux runs use Rust 1.99.1 and therefore also exercise the Clippy fix in §4;
the macOS run uses 1.97.1, where that lint does not exist yet, so the two
toolchains together cover both sides of the drift.

## 6. Remaining limitations

- Windows: the workflow is written but has never executed, and Windows has never
  been run by hand here. It stays a preview target.
- Native Linux x86-64: validated under Rosetta only.
- `ubuntu-24.04-arm` requires a public repository.
- CI runs `kode fmt`, not `cargo fmt`: the tree has pre-existing rustfmt drift in
  files this work does not touch.
- Old clang (< 15) is untested; the generated IR assumes a modern clang.
