# B6: CLI integration and conformance

> Historical: B8 removed Cranelift; the two-backend comparisons below were the
> evidence used at B6 and have since been replaced by single-backend checks.

Stage B6 of ADR 0035. B1–B5 lived inside `crates/kode-llvm` and used their own
single-file front end, which is why `modules_alias.kode` could not be built. B6
wires the backend into the real CLI, so programs are loaded, merged and checked
exactly as Cranelift programs are, and then compares the two backends over the
whole suite.

## Changes

| File | Change |
|---|---|
| `crates/kode-cli/Cargo.toml` | `kode-llvm = { path = "../kode-llvm" }` |
| `crates/kode-cli/src/args.rs` | `Backend` enum (default `Cranelift`), `--backend=cranelift\|llvm`, help line, unknown names rejected with exit 2 |
| `crates/kode-cli/src/main.rs` | `object_for` dispatches on the flag; `llvm_object` emits IR, compiles it with clang into a temporary object and returns the bytes |
| `crates/kode-cli/tests/llvm_conformance.rs` | new integration tests driving the real binary |
| `README.md`, `CHANGELOG.md` | the flag is documented as experimental |

Nothing changed in MIR, the runtime, Cranelift, the linker or the default path:
`kode_codegen::compile_to_object` is still what runs without the flag.

Import/package loading needed **no work**: `driver::load` already merges the
modules and packages into one `Program`, and `object_for` receives MIR, so the
LLVM backend sees the same merged program. `modules_alias.kode` therefore builds
and runs through `kode build --backend=llvm` with no backend change.

A missing clang is reported as `kode: the LLVM backend needs ...` and exits 1 —
never a quiet fallback to Cranelift. IR or object-file errors are surfaced with
the clang stderr.

## Conformance results

`cargo test -p kode-cli --test llvm_conformance` — 6 tests, 14.5 s wall clock:

| Suite | Programs | Result |
|---|---|---|
| `tests/run-pass` | 45/45 (three batches of 15) | exit status, stdout and stderr identical to Cranelift; matches each `.out` |
| `examples/*.kode` (non-server) | 8/8 | identical exit status, stdout and stderr |
| `tests/compile-fail` | 98/98 | both backends reject with the same exit status and byte-identical diagnostics |
| flag handling | — | `--backend=wat` exits 2 with a clear message; `--backend=cranelift` still builds |

Every run used `KODE_LEAK_CHECK=1` and a 30 s timeout, so a leak report would
show up as a stderr difference and a hang fails instead of stalling the suite.

Both backends also agree on `kode run --backend=llvm examples/hello.kode`
(exit 0, `hello world`).

## What this does and does not prove

Proven: on this machine (macOS arm64, clang from the installed LLVM), the LLVM
path builds every program the Cranelift path builds, including imports, and
produces the same output, errors, exit codes and leak-free behaviour.

Not proven: other targets and clang versions, `-g`/debug info, LTO,
cross-compilation, and performance parity as a policy (B3 recorded the measured
numbers). The default backend is unchanged.

`kode test` shares `object_for`, and was spot-checked: `kode test
tests/kode-test/passing.kode --backend=llvm` reports `2 passed, 0 failed` and
exits 0, the failing fixture exits 1 on both backends. It is not part of the
automated conformance suite.
