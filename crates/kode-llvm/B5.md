# B5: errors and concurrency

Stage B5 of ADR 0035. As with objects, no emission change was needed: `throw`,
`catch`, `spawn`, `await`, `send`, `recv` and `close` all reach the backend as
ordinary calls and branches that B1 already lowers. B5 proves the protocol and
the ABI against the runtime, and adds the tests that would catch a broken thunk,
a missing reference flag or a leaked pending error.

## Error MIR operations and lowering

| MIR | Emission | Runtime |
|---|---|---|
| `ErrThrow(v)` | `call void @"kode_err_throw"(i64 v)` | `error.rs`: stores in the pending slot |
| `ErrPending()` | `call i64 @"kode_err_pending"()` after every call that can raise | returns the pending value or 0 |
| `ErrTake()` | `call i64 @"kode_err_take"()` at a `catch` | clears and returns the pending value |
| `unwrap` of `none` | `call void @kode_unwrap_fail(line)` | same message and hint as Cranelift |

There is **no LLVM exception machinery**: no `invoke`, no `landingpad`, no
personality function. That is asserted, because inventing unwinding would change
cleanup order and error identity.

Uncaught errors print `kode: error: <message>` (plus ` (code N)` for an
`Error`) and exit with status 1 — matched exactly, including the message text.

## Concurrency MIR operations and lowering

| MIR | Emission | Runtime ABI |
|---|---|---|
| `spawn f(args)` | `kode_task_spawn(ptrtoint @kode_thunk_i, args..., is_ref)` | `task.rs`: thunk `fn(i64)->i64`, flag 1 when the result is a reference |
| `await t` | `kode_task_await(t)` | joins and returns the value |
| `await t catch e` | same call, then pending check | failure is a pending error in the awaiting task |
| `channel()` | `kode_chan_new()` | `channel.rs` |
| `send(ch, v)` | `kode_chan_send(ch, v, is_ref)` | `is_ref` mirrors the value's kind |
| `recv(ch)` | `kode_chan_recv(ch)` | blocks until a message or close |
| `close(ch)` | `kode_chan_close(ch)` | pending messages stay receivable |

Verified signatures in emitted IR: `kode_task_spawn(i64,i64,i64)`,
`kode_task_await(i64) -> i64`, `kode_chan_send(i64,i64,i64)`,
`kode_chan_recv(i64) -> i64`, `kode_chan_close(i64)`, `kode_chan_new() -> i64` —
identical to `kode-rt`.

## Ownership and cleanup findings

- `throw` does not skip cleanup: MIR releases locals on the way out, so an error
  raised after building an object with a string field and a string list leaks
  nothing (500-object loop test, both backends, leak checks on).
- The pending error owns its value until `kode_err_take`; rethrowing from a
  `catch` block releases the caught message and installs a new one (asserted via
  two `kode_err_throw` calls, leak-checked by the nested test).
- Reference values sent through a channel are retained by the channel and
  released by the receiver; objects with strings and lists survive a
  send/recv/close cycle with no leaks.
- Tasks returning strings set the reference flag; the awaiting task takes
  ownership and releases it. 300 task results and 100 strings over a channel run
  leak-free.
- No double free, use-after-free or leaked reference showed up under
  `KODE_LEAK_CHECK=1` in any test.

## Tests added (14, all new files)

`tests/errors_concurrency.rs` (8 end-to-end): uncaught error + status 1,
three-level propagation, errors after allocation in `for` and `while` loops
(1,000 iterations), nested catch with rethrow and early return from `catch`,
task failure at `await` (both `catch` forms), objects/strings through a channel
with messages pending at `close`, two producers and two consumers, 300 tasks and
20 producers sending strings.

`tests/ir_errors_concurrency.rs` (6): pending-error protocol and absence of
`invoke`/`landingpad`, `kode_err_take`, thunk + reference flag for a string
result, the four channel calls with the reference flag, tasks in a list, and
rethrow from a catch block.

Every program runs with `KODE_LEAK_CHECK=1` under a **20 s wall-clock timeout**
that kills the child on expiry, so a deadlock fails the test instead of hanging.

## Parity measured

| Program | LLVM rc / stdout / stderr | Cranelift | Deadlock? |
|---|---|---|---|
| uncaught, propagate | identical (status 1) | identical | no |
| loop_alloc, nested_catch | identical (status 0) | identical | no |
| task_errors, chan_refs, chan_mpmc, task_many | identical (status 0) | identical | no |
| empty open channel (`recv`) | blocks, killed at 3 s | blocks, killed at 3 s | **yes, by design** |

Timings (best of three, arm64): 200k channel send/recv round trips — Cranelift
0.017 s, LLVM 0.017 s; 300 tasks + strings — 0.006 vs 0.007 s; two producers /
two consumers — 0.002 s both. hello world unchanged at 1,077,584 bytes.

Run-pass: 44/45 programs byte-identical with empty stderr (`modules_alias.kode`
still needs the CLI loader); workspace **179 tests pass** with leak checks.

## Unsupported, unproven or surprising

- **`?.` on an optional primitive is rejected by the front end** (`E0219`),
  observed while writing the B4 optional test. Backend unrelated, but worth
  recording.
- Errors carry the thrown message only; the uncaught format has no source line
  for string throws (only `unwrap` reports a line). That is the current
  language behavior, reproduced, not changed.
- **Not tested**: task cancellation or timeouts (the language has none), nested
  `try`/`finally`, select/racing receives, a receive from a channel whose
  producer task failed, and programs where a task outlives `main` (the runtime
  joins, but only the "unused spawn" case in `tests/run-pass/tasks.kode` covers
  it). Do not read B5 as a claim about those.
- A program that receives from an empty, unclosed channel deadlocks on **both**
  backends; that is the program's bug, and the suite's timeout is what keeps it
  from hanging CI.
- Single-file programs only; no `--backend` flag, Cranelift remains production.
