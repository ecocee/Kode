# B4: objects, methods, dispatch and generics

Stage B4 of ADR 0035. No new emission code was required: object construction,
field access, methods and dispatch all reach the backend as `Call`, `Load`,
`Store`, `Retain`, `Release` and `CallIndirect`, which B1 already emits. B4's
work is proving the layout and ownership against the runtime and Cranelift, and
locking that behaviour in with tests.

## Object MIR operations and their lowering

| Operation (MIR) | Emission | Evidence in the runtime |
|---|---|---|
| `Call` to `ObjNew` / `ObjNewClass` | `call i64 @"kode_obj_new_class"(nfields, refmask, class_id)` | `object.rs`: size `24 + 8 * nfields`, `kind = OBJ | (class_id & 0xff) << 8 | nfields << 16` |
| slot 2 (offset 16) | written by the runtime | `*((p as *mut i64).add(2)) = refmask` |
| field read | `getelementptr i8, ptr %obj, i64 (24 + 8*i)` then `load` | `lower/data.rs`: `offset = 24 + 8 * fi` |
| field write | same `getelementptr`, then `store` | object initialisation and assignment share the slot |
| reference field write | MIR stores the new value, then `kode_release`s the value it replaced | leak checks below |
| method call | direct `call i64 @"kode_fn_Class.method"(receiver, args...)` | MIR names methods with their class |
| interface call | generated `kode_fn_Interface.method(obj)` dispatch function; tested by behaviour | `plan_dispatches` in `kode-mir` |
| closure / function value | `CallIndirect`: code at offset 24, `inttoptr`, indirect call | `object.rs` closure layout |
| optional object | `none` is `i64 0`; `!` calls `kode_unwrap_fail(line)` | `error.rs` message + hint |
| generic over a class | monomorphised name, e.g. `kode_fn_first.cls_Pair` | `kode-mir` instantiation |

No new layout, offset or ABI was invented; the IR uses the offsets MIR supplies,
which the runtime defines.

## Ownership and cleanup

- Field slots that hold references are retained and released by MIR, not by this
  backend: B4 only emits what MIR carries. Assigning a string field emits
  `store` then `kode_release` of the old value, matching Cranelift.
- Objects are released at end of scope on every path; the 2,000-iteration
  early-return test with string fields runs leak-free.
- String literals have a static refcount (`-1`) and are not retained; this is
  now asserted, because it is easy to "fix" wrongly.
- `none` is always an explicit `i64 0` store; no `undef` appears in object IR
  (asserted).
- Aliasing (`b = a`) shares one object; both bindings release their own owner.

## Tests added (16, all new files)

`tests/objects.rs` (8 end-to-end, each with `KODE_LEAK_CHECK=1`): fields,
methods, defaults and mutation; nested object + list + map fields; aliasing and
reference identity; 2,000 early-returning constructions with string fields;
optional objects (`none`, `!`, `??`); interface dispatch over two classes;
generics instantiated for a class; unwrapping `none` stops with the runtime's
message and hint.

`tests/ir_objects.rs` (8): `nfields`/`refmask`/class id at allocation, field
slots at 24/32, release-after-store for reference fields, class-qualified method
symbols, the interface dispatch function, optional null + unwrap guard,
monomorphised generic names, and no `undef`.

Crate total **50 tests**; workspace **165 tests pass** with `KODE_LEAK_CHECK=1`.

## Unsupported or out of scope

- `?.` that would need an optional *primitive* result is rejected by the
  front end (`E0219`) — a language limitation, not this backend.
- Objects inside tasks/channels follow the same generic paths and are covered by
  the run-pass sweep, but no dedicated task-object test was added at B4.
- Single-file programs; no imports, packages or `kode.toml`.
- No debug info, `-g`, LTO or cross-compilation.
- Not integrated: no `--backend` flag; Cranelift is still the production
  backend. **Object parity is tested for the shapes above, not proven
  exhaustively** — nested generics over interfaces, for example, are exercised
  only through `tests/run-pass`.
