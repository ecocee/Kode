# B8: Cranelift removal and the process fix

Stage B8 of ADR 0035, in two commits: `refactor: remove cranelift backend` and
`fix: correct process execution errors on linux`.

## Part A: Cranelift is gone

| Removed | What used it |
|---|---|
| `cranelift-codegen`, `-frontend`, `-module`, `-object`, `-native` (workspace + lock) | `kode-codegen` |
| `crates/kode-codegen/src/function.rs` (525 lines) | the Cranelift lowering |
| `crates/kode-codegen/src/runtime.rs` (158 lines) | the Cranelift `RtFn` ABI table |
| `kode_codegen::compile_to_object` | `kode-cli`'s Cranelift branch |
| `args::Backend`, the dispatch in `object_for` | the CLI's backend selection |

`kode-codegen` (renamed `kode-link` in B9) survives as the shared **linker only** (`link.rs`, 94 lines,
unchanged): it writes the object next to the output, invokes `KODE_CC`/`CC`/`cc`
with the runtime archive, strips on `--release`, and removes the temporary object.
`kode-llvm` and `kode-cli` both call it, so the linker was preserved, not moved.

The flag: `--backend=llvm` is accepted as a no-op for scripts written during the
migration. `--backend=cranelift` exits 2 with "the Cranelift backend was removed;
LLVM is the only backend", and any other name exits 2 naming LLVM. There is no
hidden implementation and no fallback.

`cargo tree` contains zero `cranelift` entries; `Cargo.lock` has none (the lock
is not tracked by git, but it was regenerated and checked).

Remaining textual occurrences, all intentional: the CLI's removal messages, ADR
0003 (historical decision record, marked superseded), the history sections of
ADR 0035, the B2–B7 stage documents (marked historical), and the B7/B8 benchmark
sections that record the old comparison.

## Part B: why `exec("missing")` did not raise on Linux x86-64

Root cause, isolated with a 20-line Rust probe in the same container:

| `std::process` path | Result for a missing program |
|---|---|
| default (glibc `posix_spawnp` fast path) | `Ok`, exit status **127**, empty stderr |
| with a `pre_exec` hook (fork + exec error pipe) | `Err(ENOENT)` |

Under Docker Desktop's Rosetta emulation, the spawned child's `exec` fails but
`posix_spawn` reports success, so Rust (and Kode) saw a program that "ran" and
exited 127. Kode's runtime used the default path, so `exec` returned a
`ProcessResult` with `code = 127` instead of throwing.

Fix, in `crates/kode-rt/src/process.rs` and `crates/kode-llvm/src/clang.rs`: add
an empty `pre_exec` hook on unix, which forces `std` to use fork/exec, where the
child's exec errno is returned through a pipe. A missing program, a bad
interpreter and a missing working directory now raise; nothing else changes
(stdin is still closed, output is still read concurrently, children are still
waited for, so no zombies).

The same hardening applies to the clang invocation: on emulated x86-64 a missing
clang used to be reported as "rejected the generated LLVM IR (exit status 127)";
it now produces the documented "the LLVM backend needs `<program>` on PATH".

## Regression tests

New `tests/run-pass/process_failures.kode` (skip-os windows): 300 repeated
failed launches each raise `cannot run`; a missing absolute path raises; a missing
working directory raises; 50 subsequent valid `/bin/sh` launches all return code
0 and the expected stdout. Existing `process.kode` (missing + empty program) and
`process_posix.kode` (exit code 3, stdout, stderr, cwd, arguments containing
spaces and `$HOME`) cover the rest.

| Requirement | Covered by |
|---|---|
| missing executable | `process.kode`, `process_failures.kode` |
| valid executable | `process_posix.kode`, `process_failures.kode` |
| nonzero exit status | `process_posix.kode` (exit 3) |
| child stdout | `process_posix.kode` |
| child stderr | `process_posix.kode` |
| arguments with spaces | `process_posix.kode` (`"a b"`, `"$HOME"`) |
| repeated failed launches | `process_failures.kode` (300) |
| cleanup after children | `process_failures.kode` (50 sequential launches; every child is waited for) |

## Validation

| Target | Compiler | Result |
|---|---|---|
| macOS 27.2 arm64 (native) | Apple clang 21.0.0 | 7/7 conformance, 186 workspace tests, 46/46 run-pass |
| Linux arm64 (native Docker) | Debian clang 19.1.7 | 7/7 conformance, 197 workspace tests |
| Linux x86-64 (**emulated**, Rosetta) | Debian clang 19.1.7 | 7/7 conformance, 197 workspace tests, `process.kode` now `true/true` |

All runs use `KODE_LEAK_CHECK=1`; run-pass output is compared with the checked-in
`.out` files, which is what `process.kode` now matches on every platform above.

Windows is still untested and `process_failures.kode` is marked `// skip-os:
windows` because it uses `/bin/sh`.

## Benchmarks

Recorded in `benchmarks/report.md` ("LLVM alone"): fib 3.5 ms, loop_mod 11.5,
mandel 12.6, sieve 29.6, collatz 196.8, lists 3.9, packed bools 3.3, maps 42.2,
JSON 89.7, strings 87.9, objects 44.5, tasks/channels 126.6, wordcount 648.3 ms.
Every case is equal to or faster than the B7 LLVM column; the B7 objects outlier
(1.39x) does not reproduce (44.5 ms both times).

## What is left

- Windows conformance, native x86-64 hardware, and older clang versions remain
  unverified.
- The IR-rejection path still reports clang's own stderr; only the "cannot start
  clang" case was hardened.
- `kode-codegen` was only a linker; B9 renamed it to `kode-link`.
